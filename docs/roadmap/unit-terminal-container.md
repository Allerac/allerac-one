# Unit Terminal Container

## Status

Implemented (pending local validation). Replaced the local, single-owner host bridge pilot
(`infra/claude-terminal/` run on the Windows host via `scripts/start-*-terminal.ps1`).

## Goal

Make the Claude Code and Codex terminals a regular part of a Unit's infrastructure:

1. The CLIs run **inside containers of the Unit**, never on the host.
2. **More than one Allerac user** of the same Unit can use the same live session,
   gated by an Allerac permission granted by an admin.

The Unit is the trust boundary. Everyone granted terminal access in a Unit shares
that Unit's terminal, its CLI logins and its workspace, and nothing outside it.

## Out of scope

- Allerac calling the terminal programmatically (headless `claude -p` / `codex exec`,
  a `/run` endpoint, agent-worker integration, terminal as an LLM provider). This is
  deferred to a later roadmap.
- Separate sessions per user or per tab. One shared session per provider stays the
  model: every tab on the same provider mirrors the same session.
- Keystroke or output recording.

## Decisions

| # | Topic | Decision |
|---|---|---|
| 1 | Host bridge | **Retired.** Remove `scripts/start-claude-terminal.ps1`, `scripts/start-codex-terminal.ps1`, `docker-compose.terminal.yml` and the `*_TERMINAL_USER_ID` single-owner model. `server.mjs` becomes the in-container process. |
| 2 | Access | Dedicated permission **`user_terminal_access`**, granted per user by an admin (Admin → user → *Unit terminal*). Admins have access implicitly. Not a domain: domains are chat agents (listed by `/api/domains`, the Control API, skills and the Unit landing). |
| 3 | CLI login | Interactive only. Logged in once inside the container through the CLI's own flow, persisted in a per-provider volume of the Unit. |
| 4 | `allerac_unit` MCP identity | A **Unit service account** with scopes chosen by an admin, replacing the per-user "Conectar API" key. |
| 5 | Workspace | Dedicated named volume of the Unit, mounted at `/workspace`. |
| 6 | Audit | Record **session lifecycle history only** (who started, reconnected, stopped; how it ended). No input content, no per-keystroke events, no output. |
| 7 | Providers | Claude Code **and** Codex. |
| 8 | Idle timeout | 30 minutes without any attached tab (unchanged). |

## Architecture

```
browser ──/api/terminal/*?provider=claude──▶ app (Next.js)
                                              │  requireCurrentUser
                                              │  hasTerminalPermission(user)
                                              │  Bearer <provider secret>
                                              ▼
                      ┌──────────────── Unit compose network ────────────────┐
                      │  terminal-claude:3015          terminal-codex:3016    │
                      │   server.mjs + claude           server.mjs + codex    │
                      │   /home/terminal ◀ claude_home  /home/terminal ◀ codex_home
                      │   /workspace ◀──── terminal_workspace ────▶ /workspace│
                      │        └── allerac_unit MCP ──▶ app:8080/api/v1 ◀──┘  │
                      └───────────────────────────────────────────────────────┘
```

- No host ports. The app reaches the services by compose DNS name.
- The browser UI is unchanged: `/terminal`, provider selector, "Abrir / reconectar".

### Compose services

One image (`infra/unit-terminal/Dockerfile`, renamed from `infra/claude-terminal/`)
with Node, `node-pty`, Claude Code and Codex at pinned versions. Two services from
that image, selected by `UNIT_TERMINAL_PROVIDER`:

- `terminal-claude` (`${ALLERAC_UNIT}-terminal-claude`)
- `terminal-codex` (`${ALLERAC_UNIT}-terminal-codex`)

Separate services rather than one container with two processes: independent logins,
restarts, resource limits and enablement. Both are opt-in through a compose profile
`terminal` (see `docs/operations/modules-and-profiles.md`).

Hardening follows the `executor` service:

- non-root user, `cap_drop: [ALL]`, `no-new-privileges`;
- `read_only: true` root filesystem with `tmpfs` for `/tmp`;
- writable mounts only: `/home/terminal` (per-provider login volume) and `/workspace`;
- memory and `pids` limits sized for the CLIs (start at 2G / 512, tune after measuring);
- egress needed: the provider's endpoints and `app:8080`. No inbound from the host.

Environment per service:

| Variable | Value |
|---|---|
| `UNIT_TERMINAL_PROVIDER` | `claude` or `codex` |
| `CLAUDE_TERMINAL_SECRET` / `CODEX_TERMINAL_SECRET` | random, ≥32 chars, generated by the installer; also given to `app` |
| `*_TERMINAL_CWD` | `/workspace` |
| `*_TERMINAL_HOST` | `0.0.0.0` (container-internal only; no `ports:`) |
| `ALLERAC_TERMINAL_API_URL` | `http://app:8080` |

`app` gets `CLAUDE_TERMINAL_URL=http://terminal-claude:3015` and
`CODEX_TERMINAL_URL=http://terminal-codex:3016` from the base compose file when the
profile is enabled. `*_TERMINAL_USER_ID` is removed.

### Volumes

| Volume | Mounted at | Holds |
|---|---|---|
| `terminal_claude_home` | `/home/terminal` in `terminal-claude` | Claude Code login, settings, history; service-account connection file |
| `terminal_codex_home` | `/home/terminal` in `terminal-codex` | Codex login (`CODEX_HOME`), config; service-account connection file |
| `terminal_workspace` | `/workspace` in both | The Unit's projects |

Both providers share `terminal_workspace`, so Claude and Codex see the same files.
An optional `TERMINAL_WORKSPACE` override may bind a host directory for development,
with the same rules as `EXECUTOR_WORKSPACE` (absolute path owned by the container
uid; never `/`, `/home` or the Allerac install folder).

These volumes hold credentials. They must be covered by the backup documentation
(`docs/database-backup-restore.md`, portable backup roadmap) as secret material.

## Access control

### Terminal permission

- Table `user_terminal_access` (migration `157_unit_terminal.sql`). Admins
  grant/revoke it in the user modal of the admin area
  (`updateUserTerminalAccess`); admins have it implicitly; service accounts
  never.
- A domain was considered and rejected: domains are chat agents and a
  `terminal` row would leak into `/api/domains`, `domainService.listAccessible`,
  skills and the public Unit landing.
- `assertTerminalAccess(user, provider)` (`src/app/lib/unit-terminal.ts`):
  provider configured (secret ≥ 32 chars) **and** `hasTerminalPermission(user)`.
- Checked on **every** proxied request (`status`, `output`, `start`, `input`,
  `resize`, `stop`), so revoking access stops a user's next poll or keystroke.
- The `/terminal` page and the taskbar/sidebar link are shown only with access.

### Bridge

- `createBridge` drops `ownerId` and the `X-Terminal-Owner` header. The service
  trusts only its bearer secret; the app is the sole authorizer and records the
  lifecycle history itself.
- Unauthenticated `GET /healthz` returns only `{ ok: true }` for the compose
  healthcheck.
- Existing protections stay: no browser CORS, `Origin` rejected at the bridge,
  same-origin check on app POSTs, fixed provider names, 32 KB body limit.

### Shared-session semantics

Unchanged from the pilot, now across users: one session per provider, every
authorized tab mirrors it, anyone attached can type, the last resize wins, closing a
tab does not end the session. The UI shows "sessão compartilhada da unit" so users
know others may be watching and typing.

Anyone with terminal access effectively controls the Unit's CLI accounts (they can
`/logout`, change settings, or read the workspace). That is the meaning of granting
`terminal`: it should be given only to people trusted with the whole Unit
workspace.

## CLI login

- The status card already reports `installed` / `loggedIn`. When logged out it shows
  the provider's login hint instead of a generic error.
- Claude Code: start the session and use its built-in login prompt (`/login`),
  which prints a URL and accepts the pasted code, all inside the browser terminal.
- Codex: `codex login --device-auth` inside the terminal session.
- Codex keeps `forced_login_method="chatgpt"` and `model_provider="openai"`; API
  keys stay stripped from the child environment.
- Logins persist in the per-provider home volume across container restarts and
  image upgrades.

Note: these are the logins of whoever signs in, and all authorized users of the
Unit share them. Check the provider's plan terms for multi-person use before
enabling this for more than one person on an individual plan.

## Unit service account for `allerac_unit` MCP

The shared session cannot act as "whoever opened it", so the MCP server runs as a
dedicated Unit identity.

### Data model (migration `157_unit_terminal.sql`)

- `users.is_service_account BOOLEAN NOT NULL DEFAULT false`.
- One service account per Unit, created on demand
  (`terminal@service.allerac.invalid`, no password hash).
- Service accounts cannot sign in: no password, and `validateSession` rejects
  them. They are excluded from the admin user list and the first-user check, and
  `updateUserRole` / `resetUserPassword` refuse them.

### Admin flow (replaces `TerminalApiConnection` per-user card)

On `/connections`, an **admin-only** card "API da Allerac no terminal da unit":

1. Admin picks scope groups from the existing `terminalApiPolicy` groups (notes,
   tickets, jobs, memory, health). Base scopes are always included.
2. Saving:
   - ensures the service account exists;
   - sets its `user_domain_access` to exactly the domains of the chosen groups (the
     API enforces route-level domain checks against the key owner);
   - creates a `control_api_keys` row for the service account with those scopes,
     7-day expiry (the bridge refuses more than 8), named `Terminal API · <provider>`;
   - installs it on **that provider's** terminal service through the existing
     `/api-connection` endpoint (one key per provider, as in the pilot UI);
   - revokes the previous managed key(s) of that provider;
   - sets the account's domain access to the union needed by all active terminal
     keys (`syncTerminalServiceAccountDomains`).
3. "Desconectar" revokes the keys first, then clears both bridge files (works when a
   terminal container is down).
4. The card shows expiry and a "Renovar" action. Expired keys simply stop working.
   Automatic renewal is out of scope.

The connection file moves from `.tools/allerac-api-{provider}.json` in the repo to
`/home/terminal/.config/allerac/terminal/allerac-api-<provider>.json` on the provider's home volume, mode
`0600`. MCP launch arguments still contain only the file path, never the token.
Non-admin users with terminal access can use the MCP tools but cannot see or change
their configuration.

## Session history (audit)

Same migration `157_unit_terminal.sql`:

```sql
CREATE TABLE terminal_session_events (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  provider    TEXT NOT NULL CHECK (provider IN ('claude', 'codex')),
  session_id  UUID NOT NULL,
  user_id     UUID REFERENCES users(id) ON DELETE SET NULL,
  event       TEXT NOT NULL CHECK (event IN ('started', 'reconnected', 'stopped', 'exited', 'idle_timeout')),
  exit_code   INTEGER,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_terminal_session_events_session ON terminal_session_events(session_id, created_at);
CREATE UNIQUE INDEX uq_terminal_session_events_end
  ON terminal_session_events(session_id) WHERE event IN ('stopped', 'exited', 'idle_timeout');
```

Recording:

- `/start` responses gain `created: boolean`. The app records `started` or
  `reconnected` with the requesting user. Recording failures are logged and
  never break the terminal.
- `/stop` records `stopped` with the requesting user.
- When the CLI exits or the idle timer fires, the bridge keeps the ended session's
  `id`, `reason` and `exitCode`. The app records `exited` / `idle_timeout` the first
  time a `status` or `output` response shows it ended. The partial unique index makes
  this idempotent across concurrent tabs.
- Never recorded: input data, input counts, output, resize events, polling.

An admin-only list on `/connections` (`GET /api/terminal/sessions`) shows the
last 100 events. Retention: 90 days, pruned when the list is loaded (there is no
scheduled cleanup job).

## Phases

1. **Container.** Dockerfile, compose services, volumes, internal URLs; bridge runs
   in-container with the existing single-owner check temporarily kept. Done when a
   login inside the container persists across `docker compose up -d --force-recreate`
   and `/terminal` works for both providers with no host processes.
2. **Shared access.** `terminal` domain, migration, access check on every request,
   bridge without `ownerId`, UI label; delete host-bridge scripts and override.
   Done when two different non-admin users with the domain see and type in the same
   session, a user without it gets 403, and revocation takes effect on the next poll.
3. **Service account MCP.** Service-account model, admin card, key install on both
   providers, login rejection. Done when `allerac_status` in either terminal reports
   the service account with exactly the admin-chosen scopes, and disconnect stops the
   tools in an already-running session.
4. **Session history.** Table, recording, admin list, retention. Done when start,
   reconnect by another user, stop, CLI exit and idle timeout each produce exactly
   one correctly attributed row, and no input data is stored.

## Tests

- Bridge: rejects missing/invalid secret and any `Origin`; no longer needs an owner;
  `created` flag; ended-session reason/exit code; connection file path and mode.
- Route: 403 without `terminal`; admin implicit access; access re-checked per request;
  `X-Terminal-User` forwarded; events recorded idempotently.
- Service account: cannot log in; key scopes ⊆ admin selection; domain access mirrors
  selection; disconnect revokes before clearing.
- Compose: config validates with and without the `terminal` profile; no `ports:` on
  terminal services.

## Open questions

- Should `/workspace` be shared with the `executor` service so agents and the
  terminal see the same projects? (Requires matching uid and a decision on agent
  write access.)
- Codex `workspace-write` sandbox inside a container that already drops
  capabilities: validate it works without extra privileges, or rely on the container
  as the sandbox.
- CLI update policy: pinned versions in the image (rebuild to upgrade) vs. allowing
  the CLIs' self-update into the home volume.
