# Provider-Independent Local Embeddings

**Status:** In progress — local baseline implemented 2026-08-01

**Priority:** High — semantic features are currently degraded

**Trigger:** GitHub Models inference was fully retired on 2026-07-30

**Affects:** RAG documents, semantic note search, semantic web-search cache, Spotify
track embeddings and recommendations

## Context

Allerac One previously generated embeddings through GitHub Models using the
hardcoded endpoint `https://models.inference.ai.azure.com`, model
`text-embedding-3-small`, and 1536-dimensional vectors.

Production-like tests on 2026-07-31 showed:

- the legacy endpoint returned `401 Unauthorized`, including with a newly-created
  fine-grained token carrying Models read access;
- the documented `https://models.github.ai/inference/embeddings` endpoint returned
  `410 Gone` with a GitHub retirement response;
- GitHub announced that the Models catalog, playground, inference API, and BYOK
  endpoints were fully retired on 2026-07-30.

This is not a deprecation of the mathematical vectors already stored. Existing
vectors remain usable for comparisons with vectors generated by the exact same
model, but Allerac can no longer generate compatible query or document vectors
through GitHub Models.

There are few indexed documents today, so preserving the existing 1536-dimensional
corpus is not a requirement. This gives us room to choose the long-term design
instead of adding another temporary provider dependency.

## Decision direction

Use a compact, locally-run embedding model as the default, initially served by the
Ollama instance already deployed with Allerac.

Do not couple semantic features directly to Ollama or to one model. Introduce a
provider-neutral embedding contract so the runtime, model, endpoint, and dimensions
can change without rewriting RAG, notes, search cache, or music features.

The initial local default is `embeddinggemma` at 768 dimensions, selected from
measurements on the target mini PC. The provider contract keeps this choice
replaceable.

## Initial benchmark result

The first benchmark on 2026-08-01 compared `embeddinggemma` and
`nomic-embed-text-v2-moe` through the deployment's Ollama container.

| Model | Dimensions | Cold | Warm | 100 inputs | Small multilingual retrieval set |
|---|---:|---:|---:|---:|---:|
| embeddinggemma | 768 | 4697 ms | 115 ms | 3106 ms | 6/6 |
| nomic-embed-text-v2-moe | 768 | 11269 ms | 324 ms | 5156 ms | 6/6 |

The evaluation set is intentionally small and must grow with real Allerac examples,
but `embeddinggemma` provided the better initial latency/resource tradeoff without an
observed retrieval-quality loss.

## Implementation progress

Completed locally on 2026-08-01:

- provider-neutral contract and Ollama adapter;
- configurable model, endpoint, dimensions, timeout, keep-alive, and version;
- strict response-count and dimension validation;
- local-first RAG, notes, semantic web cache, and Spotify consumers;
- keyword fallback for note search when embeddings are unavailable;
- migration from 1536 to 768 dimensions with versioned runtime state;
- resumable document/Spotify reindex script;
- all 804 Spotify vectors regenerated with `embeddinggemma`;
- benchmark harness and focused unit/API tests.
- protected `/benchmark/embeddings` UI for selecting installed models, running the
  comparison, viewing first/warm/batch/retrieval results, and keeping recent
  browser-local history.

Still required before calling the roadmap complete:

- expand the retrieval evaluation set with real user-approved examples;
- expose embedding health/model identity in the operational Health/Admin UI or API;
- add explicit interactive/background prioritization for larger indexing workloads;
- validate the rebuilt application through the normal release workflow.

## Principles

1. **Local-first, not local-only.** Local embeddings are the default, while the
   contract permits an optional external provider if a deployment needs one.
2. **Model identity is data.** Persist provider/runtime, model ID, dimension, and
   embedding version alongside or unambiguously associated with every vector.
3. **Never mix vector spaces.** Vectors from different models must not be searched
   or averaged together, even when their dimensions match.
4. **Dimension is not a quality score.** A good 384- or 768-dimensional model may
   outperform a 1536-dimensional model while using less memory and storage.
5. **Reindexing is a supported operation.** Changing models must be an explicit,
   resumable process rather than an emergency database rewrite.
6. **Chat remains available.** If local embedding generation is unavailable or
   times out, non-semantic chat must continue with a visible degraded-mode signal.
7. **Interactive work has priority.** Query embeddings needed for chat take
   precedence over background document or music indexing.

## Proposed target architecture

Define a small contract such as:

```ts
interface EmbeddingProvider {
  embed(texts: string[]): Promise<number[][]>;
  providerId(): string;
  modelId(): string;
  dimensions(): number;
}
```

The exact TypeScript shape may change during implementation. The important boundary
is that consumers depend on the contract, not on a GitHub token, an Ollama URL, or a
specific model name.

Configuration should distinguish embedding settings from chat-provider settings.
At minimum it must support:

- provider/runtime;
- endpoint;
- model ID;
- expected dimensions;
- request timeout;
- batch size and concurrency;
- keep-alive behavior where supported;
- degraded-mode policy.

## Mini-PC performance strategy

Using Anthropic for chat and Ollama only for embeddings is expected to be a suitable
split for a mini PC. Embedding generation is a bounded forward pass and is much
lighter than locally generating a long chat response. It still needs measurement:
RAG query latency is added before the Anthropic call, and bulk indexing can compete
for CPU and RAM.

The implementation should therefore:

- keep interactive query embedding latency bounded with a short timeout;
- process documents and Spotify tracks through background work with low concurrency;
- batch background inputs where the selected model/runtime benefits from it;
- prevent bulk indexing from starving interactive queries;
- avoid embedding generation in domains and operations that do not use semantic
  retrieval;
- cache repeated embeddings where correctness and storage limits permit;
- select an intentional Ollama keep-alive policy to balance warm latency and RAM;
- expose health, latency, queue depth, failures, and active model identity.

## Benchmark before model selection

Evaluate a small shortlist of compact local embedding models on the actual mini PC.
Do not select a model from dimension count or public leaderboard position alone.

Measure:

1. cold-start time;
2. warm single-query latency;
3. throughput for 100 representative chunks;
4. resident RAM and CPU usage;
5. impact while the normal Allerac containers are running;
6. behavior under one interactive query during background indexing;
7. retrieval quality in Portuguese, Spanish, and English;
8. document, note, and music-metadata retrieval separately;
9. maximum useful input/chunk size;
10. operational behavior after restart and when Ollama is unavailable.

Create a small versioned evaluation set containing representative queries, expected
relevant chunks, hard negatives, paraphrases, and cross-language queries. Compare at
least recall at 5 and inspect failures manually. The chosen model must meet an agreed
latency/RAM envelope and retrieval threshold before schema changes are finalized.

## Phased delivery

### Phase 1 — Inventory and baseline

1. Inventory every `EmbeddingService` consumer and every `vector(...)` column,
   function, index, cache, and hardcoded dimension.
2. Count current vectors and confirm that destructive reindexing is acceptable.
3. Capture current container resource usage on the mini PC.
4. Build the multilingual retrieval evaluation set.

### Phase 2 — Benchmark and choose

1. Select a small shortlist of local models supported by the chosen runtime.
2. Run cold, warm, batch, contention, and retrieval-quality benchmarks.
3. Record results and choose the default model and dimension.
4. Define timeout, concurrency, batching, and keep-alive defaults.

### Phase 3 — Introduce the provider boundary

1. Add the provider-neutral embedding contract and configuration.
2. Implement the local Ollama adapter.
3. Remove GitHub-token knowledge from embedding consumers.
4. Add model identity and dimension validation at startup and write time.
5. Add health reporting and degraded-mode behavior.

### Phase 4 — Schema and reindexing

1. Migrate vector columns and search functions to the chosen dimension and version.
2. Update HNSW indexes and all fixed-dimension calculations.
3. Add a resumable, observable reindex command/job.
4. Reindex the small existing corpus and validate counts and retrieval quality.
5. Ensure partial or failed reindexing cannot mix incompatible vector spaces.

### Phase 5 — Workload isolation

1. Prioritize interactive query embeddings.
2. Move bulk document, notes, and music indexing to bounded background work.
3. Add retry/backoff and idempotency.
4. Add metrics or structured logs for latency, errors, active model, and queue depth.

### Phase 6 — Remove retired integration

1. Remove the GitHub Models endpoint and embedding-specific GitHub credential
   requirements.
2. Update Admin copy, onboarding, environment examples, tests, and documentation.
3. Keep GitHub credentials only for capabilities that still genuinely use GitHub.

## Definition of done

- Allerac generates embeddings locally without a GitHub Models dependency.
- RAG, notes, semantic search cache, and music use the provider-neutral contract.
- The active runtime, model, dimension, and version are observable.
- Interactive chat remains usable when embeddings are unavailable.
- Background indexing cannot monopolize the mini PC.
- All stored vectors belong to a known compatible vector space.
- Reindexing is resumable and tested.
- The selected model meets the agreed multilingual retrieval and mini-PC resource
  thresholds.
- Documentation and Admin UI no longer claim that GitHub Models provides embeddings.

## Deferred and out of scope

- Implementing the migration in the current documentation session.
- Preserving compatibility with the small existing GitHub-generated corpus.
- Selecting the final local model without hardware and retrieval benchmarks.
- Using local Ollama for chat generation; Anthropic and other chat providers remain
  independent from the embedding decision.

## Open questions for implementation

- Which compact models enter the first benchmark shortlist?
- Should model/version metadata live on every row, on an embedding collection, or
  both?
- Should each semantic feature have an independent collection/version lifecycle?
- What latency, RAM, and recall thresholds define acceptance on the mini PC?
- Is Ollama the permanent local runtime or the first adapter behind the contract?
- Which background queue should own document and music reindexing?
